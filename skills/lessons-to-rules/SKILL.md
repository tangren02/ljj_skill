# 把经验筛选成规则

目标：同一类问题不再出现。不是每次纠正都要新增规则；本次没有值得保存的规则，也是正常结果。

## 步骤

1. **收集问题。** 回顾本次会话，找出：
   - 用户明确纠正过的地方（"不要……"、"我说的是……"、"太多了"）
   - 用户撤销、删除或要求重做的改动
   - 用户在本次请求里直接描述的问题
   只记录用户表达过不满的行为，不要自己猜测或扩展。会话较长或上下文已被压缩时，早期的纠正可能已经看不到；只依据当前能看到的内容，并在第 7 步说明这一点。

2. **筛掉一次性要求。** 判断每个问题是长期偏好，还是只针对这一次任务。例如"这次不用写测试"是一次性要求，不能推导成"以后都不写测试"。拿不准的，在第 6 步展示时标注出来，由用户决定。

3. **找根因，按"类"归纳，但不扩大范围。** 不写"不要在 utils.py 第 40 行加 try/except"，而是写出这类行为本身，同时保留原问题的条件，例如"已经由调用方校验过的参数，不在被调用函数里重复校验"。证据只支持局部规则时，就写局部规则。一类问题一条规则。只适用于某个模块、目录或任务类型的规则，要在规则里写明范围。

4. **写成规则。** 每条规则：
   - 一句话，说清楚**该做什么**（不只是不该做什么）
   - 保留适用条件，避免一刀切（写"代码未变化时不重复运行已通过的检查"，而不是"检查只跑一次"）
   - 能检查：读完后能判断智能体有没有遵守
   - 不写空话（"写高质量代码"、"小心谨慎"这类没用）

5. **对照现有规则。** 先确定仓库根目录：在当前工作目录运行 `git rev-parse --show-toplevel`。不在 git 仓库中，或结果与用户正在工作的项目明显不符时，询问用户规则写到哪里，不要自行猜测。读取根目录的 AGENTS.md（不存在则准备新建）。对每个问题判断：
   - **没有相关规则** → 新增
   - **有规则但写得含糊** → 改写那一条，不要重复添加
   - **规则已经写得清楚，智能体仍然违反** → 不要改得更重或再加一条；在第 6 步告诉用户这条规则已存在但没被遵守，并附上可选的处理办法，由用户选择或都不采用：
     - 把这条规则挪到所在小节中更靠前、更显眼的位置
     - 改写成更容易检查的形式（例如写出具体的判断条件或触发场景）
     - 维持原样
   - **与已有规则冲突** → 指出冲突，让用户决定

6. **给用户确认。** 展示目标文件路径，以及要新增、修改、合并或删除的规则（diff 形式），每条附一句它对应本次会话中的哪次纠正（这句只用于确认，不写入文件）。不顺带清理与本次问题无关的规则。用户同意后再写入：新增的规则写到 `## 工作规则（从实际问题中总结）` 一节，没有这一节就在文件末尾创建；修改已有规则时在原位置改写，不挪动它所在的小节，除非用户在确认时要求移动。只写仓库根目录的 AGENTS.md，不写全局文件。

7. **简短汇报。** 一句话说明加了几条、改了几条。如果第 1 步提到的早期纠正可能看不到，一并说明本次只覆盖了当前上下文中能看到的部分。

## 规则格式参考

以下仅示意格式，不要写入 AGENTS.md：

```markdown
## 工作规则（从实际问题中总结）

- 代码和相关环境未变化时，不重复运行已通过的检查；有相关改动后，只重跑受影响的检查。
```

## 注意

- 规则越少越有效。宁可 10 条被遵守，也不要 50 条被忽略。能合并就合并，不要只增不减。
